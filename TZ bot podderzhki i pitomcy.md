# Техническое задание
## Telegram-бот поддержки с системой ролей и модулем «Питомцы»

---

## ЧАСТЬ 1. Бот поддержки (форум-топики + роли)

### 1.1. Общая механика
- Юзер (ПЗ) пишет боту в личные сообщения.
- Бот создаёт отдельную тему (topic) в группе-форуме для этого обращения.
- Все сообщения ПЗ пересылаются в тему; ответы админов из темы пересылаются ПЗ.
- Тема имеет статусы: `open` (не взята), `claimed` (в работе у админа), `spec` (передана спец-админу), `closed` (завершена).

### 1.2. Роли
Иерархия ролей (от младшей к старшей), права нарастают — у кого ранг выше, тому доступно всё, что доступно нижестоящим, плюс своё:

| Роль | Уровень (role_level) |
|---|---|

| Админ | 1 |
| Спец админ | 2 |
| Ст. админ | 3 |
| Тех. Админ | 4 |
| Овнер | 5 |

Роли хранятся в таблице `admins`: `user_id`, `role`, `role_level`, `added_by`, `added_at`.

Проверка прав в коде сводится к сравнению чисел: `если role_level ≥ N → действие разрешено`, где N — минимальный требуемый уровень для конкретного действия (см. 1.3, 1.6).

### 1.3. Команда `/spec`
- Доступна ролям с `role_level ≥ 3`: Спец админ, Ст. админ, Овнер.
- При вызове в теме — статус темы меняется на `spec`.
- С этого момента бот проверяет **каждое входящее сообщение** в теме:
  - автор с `role_level ≥ 3` (Спец админ / Ст. админ / Овнер) → сообщение остаётся;
  - автор с `role_level < 3` (Мл. админ / Админ) → сообщение **автоматически удаляется** ботом, автору приходит уведомление «доступ ограничён».
- Обратная команда `/unspec` — снимает статус (доступна тем же ролям, `role_level ≥ 3`).

### 1.4. Требования к надёжности
- Проверка роли выполняется **на каждое действие**, а не один раз при входе в тему.
- Ведётся журнал действий: кто, когда, какую тему открыл/закрыл/пометил как spec.
- Сообщения ПЗ доставляются в тему **независимо** от статуса — блокируется только запись обычных админов, не чтение/приём сообщений от пользователя.

### 1.5. Очередь ожидания
- Если тема в статусе `open` дольше X минут (задаётся в конфиге) — ПЗ получает сообщение с предложением открыть мини-приложение (раздел «Игры», п. 2.5).
- Как только тема переходит в `claimed`/`spec` — рассылка предложений прекращается.
- Сообщения ПЗ, отправленные во время «игры на ожидание», в любом случае идут в тему поддержки без задержек и не теряются в интерфейсе мини-аппа.

### 1.6. Рассылка (`/ad`, `/ads`)

**Доступ:** только Ст. админ и Овнер (`role_level ≥ 4`).

**Создание черновика — `/ad`:**
1. Автор (Ст. админ/Овнер) вызывает `/ad`.
2. Бот переводит этого юзера в FSM-состояние «ожидание контента для рассылки», привязанное к его `user_id`.
3. Следующее сообщение этого же автора (текст/фото/видео) бот перехватывает и сохраняет как черновик в таблицу `broadcasts`: `id`, `content`, `created_by`, `status = draft`, `created_at`.
4. FSM-состояние сбрасывается, бот подтверждает создание черновика с его номером.
5. Таймаут ожидания контента (например, 10 минут) — если автор ничего не прислал, состояние сбрасывается само.

**Просмотр — `/ads`:**
- Показывает список всех черновиков (id + превью текста + статус).
- При выборе конкретного — 3 кнопки:
  - **Редактировать** — бот ждёт новое сообщение от автора и перезаписывает содержимое черновика (тот же id).
  - **Отправить** — запрашивает повторное подтверждение («точно разослать всем?»), затем рассылает контент всем `user_id` из базы пользователей бота, с задержкой между отправками (во избежание лимитов Telegram). Статус меняется на `sent`, фиксируется `sent_at`.
  - **Удалить** — удаляет черновик (или помечает `status = deleted`).

**Обработка ошибок при отправке:**
- Если пользователь заблокировал бота — ошибка логируется, юзер помечается неактивным, рассылка не прерывается.
- По завершении автору приходит отчёт: «Отправлено: X, не доставлено: Y».

**Ограничение:** «Редактировать» и повторная отправка недоступны для черновика в статусе `sent` — для нового текста создаётся новая рассылка через `/ad`.

### 1.7. Переименование тем
- Название и иконка темы (topic) меняются штатными средствами Telegram (значок редактирования в форуме) — отдельная функциональность бота не требуется.
- Требование: бот не должен перехватывать/блокировать сервисное событие изменения темы (`forum_topic_edited`).

## ЧАСТЬ 2. Модуль «Питомцы» (Telegram Mini App)

### 2.1. Виды питомцев (7)
Кошка, Собака, Лиса, Панда, Кролик, Ёжик, Пингвин.

- Вид выбирается/определяется один раз — на переходе стадии «Яйцо → Малыш» (см. 2.2).
- До этого момента питомец визуально одинаков для всех видов (Зарождение, Яйцо).

### 2.2. Стадии роста (5)
Зарождение → Яйцо → Малыш → Подросток → Взрослый.

**Условие перехода между стадиями:**
- Накопление XP («очков ухода») за действия (п. 2.4) — порог для каждой стадии задаётся отдельно (баланс подбирается тестированием).
- Дополнительное условие: все параметры (п. 2.3) не ниже 60% на момент перехода — иначе переход откладывается до восстановления параметров.
- Регресс стадии не предусмотрен. При критическом падении параметров — «заморозка» роста (XP не начисляется), но стадия не понижается.

### 2.3. Параметры питомца (6)
| Параметр | Поведение |
|---|---|
| Голод | падает со временем, поднимается действием «Покормить» |
| Счастье | падает со временем, поднимается действием «Поиграть» |
| Гигиена | падает со временем, поднимается действием «Помыть» |
| Энергия | падает от действий (особенно «Тренировать»), восстанавливается «Сном» |
| Дисциплина | падает со временем, поднимается «Тренировкой» |
| Лапки | растёт от «Тренировки», влияет на шанс победы в играх (п. 2.5) |

- Диапазон каждого параметра: 0–100.
- Падение — по таймеру (например, раз в час на N%, значение конфигурируется).
- При достижении 0 по любому параметру — питомец переходит в состояние «грустит»/«болеет» (визуальный статус), XP не копится.

### 2.4. Действия (5) и их эффект
| Действие | Требует ресурс | Эффект |
|---|---|---|
| Покормить | 1 ед. еды из инвентаря | +Голод |
| Поиграть | игрушка (опц.) | +Счастье |
| Помыть | — | +Гигиена |
| Уложить спать | недоступно, если Энергия = 100 | +Энергия (по таймеру сна) |
| Тренировать | требует Энергию | +Дисциплина, +Лапки, −Энергия |

- Каждое действие имеет кулдаун (не даёт спамить одно и то же).
- Каждое выполненное действие увеличивает соответствующий счётчик в статистике (п. 2.9).

### 2.5. Мини-игры (3)
Призрачный куб, Шёпот цифр, Проклятая загадка.

- Победа даёт валюту (монеты); проигрыш — либо ничего, либо небольшое утешительное начисление.
- Параметр «Лапки» повышает шанс победы (конкретная формула — на усмотрение баланса).
- Игры используются как контент для экрана ожидания (см. 1.5).

### 2.6. Магазин
**Еда (6):** Призрачное мясо, Лунные ягоды, Туманный суп, Эфирный нектар, Теневой десерт, Звёздный корм — расходники, списываются через кнопку «Использовать».

**Игрушки (5):** Светящийся мяч, Призрачная мышка, Магический волчок, Теневой клубок, Ловец снов — расходники или ограниченного использования (уточнить с заказчиком).

**Аксессуары (9):** Призрачный ошейник, Плащ невидимости, Лунный кулон, Теневой венок, Плащ теней, Призрачный бант, Ожерелье, Корона ночи — разовая покупка, косметика, не влияет на параметры, остаётся в инвентаре навсегда.

**Фоны (5):** Заколдованный лес, Призрачный замок, Лунная поляна, Туманное болото, Звёздная бездна — разовая покупка, применяются как фон экрана питомца.

Все покупки — кнопка «Купить» (списывает валюту), применение — кнопка «Использовать».

### 2.7. Валюта и экономика
- Источник валюты: победы в играх (2.5), возможно — бонус за активность в поддержке (сообщения, ежедневный вход).
- Расход валюты: покупки в магазине (2.6).
- Экономику (курсы, цены, награды) нужно закладывать с запасом на баланс-тестирование — точные числа не фиксируются в этом ТЗ, задаются отдельным документом/таблицей баланса.

### 2.8. Достижения (18)
Новичок, Друг питомца, Сердце питомца, Легенда, Вечная связь, Азартный игрок, Король кубиков, Гадалка, Заботливый хозяин, Чистюля, Соня, Призрачный капитал, Тень богатства, Коллекционер, Фоновый маг, Преданный дух, Призрачный страж, Повелитель духов.

Каждое достижение — условие, проверяемое после релевантного действия:
| Группа | Проверяемая метрика |
|---|---|
| Новичок / Друг питомца / Сердце питомца / Легенда / Вечная связь | уровень «привязанности» — серия дней ухода за питомцем |
| Азартный игрок / Король кубиков / Гадалка | кол-во игр/побед по каждой из 3 игр |
| Заботливый хозяин / Чистюля / Соня | кол-во кормлений / купаний / снов |
| Призрачный капитал / Тень богатства | накопленная валюта (пороги) |
| Коллекционер / Фоновый маг | кол-во купленных предметов / фонов |
| Преданный дух / Призрачный страж / Повелитель духов | серия ежедневных входов (самые редкие) |

Точные числовые пороги для каждого достижения нужно зафиксировать отдельно (таблица баланса), в этом ТЗ фиксируется только логика проверки.

### 2.9. Навигация Mini App (5 разделов)
Питомец · Игры · Дом · Магазин · Профиль

- Единое нижнее/верхнее меню, переключение без перезагрузки состояния.
- Раздел «Дом» — предположительно место применения фонов/декора (уточнить у заказчика точное назначение).

### 2.10. Инвентарь — общие элементы UI
- Кнопка «Использовать» — применяет предмет (еда/игрушка).
- Кнопка «Купить» — списывает валюту, добавляет предмет в инвентарь.
- Кнопка «Назад» — навигация на предыдущий экран.

### 2.11. Статистика в профиле (8 метрик)
Сообщений, Игр сыграно, Побед в играх, Серия побед, Кормлений, Купаний, Снов, Тренировок, Серия входов.

- Все метрики инкрементируются соответствующими действиями в реальном времени.
- Используются как источник данных для проверки достижений (2.8).

## ЧАСТЬ 3. Технические требования

### 3.1. Архитектура данных (минимальный набор таблиц)
- `users` (юзеры бота поддержки)
- `admins` (роли)
- `topics` (темы поддержки: id, статус, claimed_by, created_at)
- `pets` (справочник видов/стадий)
- `user_pets` (питомец конкретного юзера: вид, стадия, параметры, XP)
- `inventory` (предметы у юзера)
- `shop_items` (справочник товаров: тип, цена, эффект)
- `achievements` (справочник) + `user_achievements` (полученные)
- `stats` (счётчики по каждому юзеру)
- `broadcasts` (черновики и отправленные рассылки: id, content, created_by, status, created_at, sent_at)

### 3.2. Взаимодействие бэкенд ↔ Mini App
- Mini App — фронтенд (HTML/JS), обращается к бэкенду бота за состоянием юзера (питомец, инвентарь, статистика) при каждом открытии.
- Все изменения состояния (кормление, покупка, победа в игре) идут через API бэкенда, а не хранятся локально во фронтенде.

### 3.3. Что нужно уточнить у заказчика до старта разработки
- Точные числовые формулы: скорость падения параметров, пороги XP по стадиям, цены в магазине, курс валюты за победу.
- Пороги для каждого из 18 достижений.
- Назначение раздела «Дом» в навигации.
- Правила выдачи вида питомца (1–7): случайно при первом получении, или выбор юзером.
- Разрешены ли дубликаты предметов/питомцев.

## Рекомендация по этапам реализации (MVP → полная версия)
1. **Этап 1** — роли и `/spec`-доступ в боте поддержки (часть 1) — минимальный риск, максимальная ценность для конфиденциальности.
2. **Этап 2** — питомец без выбора вида, 3–4 параметра, 2 действия, без магазина — проверка гипотезы вовлечения.
3. **Этап 3** — полный набор параметров/действий, 1 мини-игра, простая экономика.
4. **Этап 4** — магазин полностью (еда/игрушки/аксессуары/фоны), достижения, статистика.
5. **Этап 5** — остальные 2 игры, полировка визуала, баланс.
