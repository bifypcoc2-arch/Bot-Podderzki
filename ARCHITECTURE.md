# Структура проекта

## Общая архитектура

```
┌─────────────────┐
│  Telegram User  │
└────────┬────────┘
         │
         ▼
┌─────────────────┐      ┌──────────────┐
│  Telegram Bot   │◄────►│   Database   │
│   (main.py)     │      │   (SQLite)   │
└────────┬────────┘      └──────────────┘
         │                       ▲
         ▼                       │
┌─────────────────┐      ┌───────┴──────┐
│  Forum Topics   │      │  Web Server  │
│   (Support)     │      │  (aiohttp)   │
└─────────────────┘      └───────▲──────┘
                                 │
                         ┌───────┴──────┐
                         │   Mini App   │
                         │ (HTML/JS/CSS)│
                         └──────────────┘
```

Бот и веб-сервер — два независимых процесса, работающих с одной базой.

## Модули и их назначение

### Основные файлы
- `main.py` — точка входа бота, инициализация и регистрация handlers
- `web_server.py` — веб-сервер для Mini App API
- `config.py` — конфигурация через pydantic-settings
- `init_db.py` — создание схемы и начальные данные
- `add_admin.py` — добавление администраторов
- `check_db.py` — проверка состояния БД

### Миграции (`alembic/`)

Схема поднимается гибридно: `Base.metadata.create_all()` создаёт недостающие таблицы при старте, а изменения уже существующих таблиц (новые колонки) выполняются миграциями Alembic. Команды и порядок работы — в `MIGRATIONS.md`.

Для SQLite в `env.py` включён `render_as_batch=True`, иначе изменение и удаление колонок не работает.

### Database (`database/`)
- `database.py` — async engine и фабрика сессий
- `models.py` — ORM модели

Основные модели: `User`, `Admin`, `AdminLog`, `AdminStats`, `Ban`, `Topic`, `Broadcast`, `UserPet`, `ShopItem`, `Inventory`, `Achievement`, `UserAchievement`, `Stats`.

### Handlers (`handlers/`)

Порядок регистрации в `main.py` значим: support → admin → broadcast → miniapp.

- `support.py` — `/start`, копирование сообщений в форум-топики, отсев забаненных
- `admin.py` — `/close`, `/spec`, `/unspec`, `/ban`, `/unban`, `/bans`, `/stats`, фильтрация сообщений в SPEC-темах
- `broadcast.py` — `/ad`, `/ads`, редактирование, отправка, удаление
- `miniapp.py` — `/pet`

### Services (`services/`)

- `support_service.py` — пользователи, топики (включая пересоздание удалённых), анонимная передача сообщений
- `admin_service.py` — проверка ролей, SPEC-режим, закрытие тем, ответы от имени бота
- `moderation_service.py` — баны и статистика по пользователям
- `anonymity.py` — генерация короткого кода из ID пользователя
- `telegram_errors.py` — разбор ошибок API: удалённая тема, недоступный пользователь, флуд-лимит и `retry_after`
- `broadcast_service.py` — черновики, отправка с задержками и повторами, защита от двойного запуска
- `pet_service.py` — создание питомцев, деградация параметров, действия, рост
- `game_service.py` — мини-игры
- `shop_service.py` — магазин и инвентарь
- `achievement_service.py` — выдача достижений

### API (`api/`)

- `auth.py` — проверка подписи Telegram initData
  - заголовок `X-Telegram-Init-Data` обязателен для всех `/api/`
  - ID пользователя берётся из подписи, а не из параметров запроса
  - подпись старше 24 часов отклоняется
- `miniapp_api.py` — endpoints: питомец, действия, статистика, инвентарь, магазин, мини-игры, достижения

### Mini App (`miniapp/`)

- `index.html` — структура
- `app.js` — загрузка данных, действия, навигация, обновление UI
- `styles.css` — стилизация

### Filters (`filters/`)

- `role_filter.py` — проверка уровня доступа администратора

## Потоки данных

### Пользовательское сообщение
```
User → Bot → Проверка бана → support_service → Database (User, Topic)
                                   ↓
                       Копия в форум-топик (без автора)
```

### Ответ администратора
```
Admin Reply in Topic → Тема закрыта?
                     → Проверка SPEC-режима
                     → Проверка уровня админа
                     → Копия пользователю от имени бота
```

### Действие с питомцем
```
Mini App → Проверка initData → POST /api/action → pet_service
                                     ↓
                        Деградация по времени → действие → запись в БД
                                     ↓
                             Новое состояние → Mini App
```

### Рассылка
```
/ad → FSM: waiting_content → черновик → Database
/ads → выбор черновика → редактировать / отправить / удалить
           ↓
     захват статуса SENDING (защита от двойного запуска)
           ↓
     отправка с задержкой, забаненные исключаются
           ↓
     прогресс пишется в БД по ходу → статус SENT
```

## Система ролей

Уровни доступа: ADMIN → 1, SPEC_ADMIN → 2, SENIOR_ADMIN → 3, TECH_ADMIN → 4, CO_OWNER → 5, OWNER → 5.

Проверка: `admin.role_level >= required_level`

Требуемые уровни по действиям:
- 1 — ответы в темах, `/close`
- 2 — доступ к SPEC-темам
- 3 — `/spec`, `/unspec`
- 4 — `/ad`, `/ads`
- 5 — `/ban`, `/unban`, `/bans`, `/stats`

CO_OWNER и OWNER по правам не различаются, разделение нужно только для отображения и журнала.

## Анонимность

- Сообщения копируются (`copy_message`), а не пересылаются: в пересланном сообщении Telegram показывает автора
- Имя темы — короткий код из SHA-256 от ID пользователя
- Ответы админов уходят от имени бота без подписи
- Обсуждения администраторов ведутся в отдельном чате, тема пользователя — только переписка с ним

## Система питомцев

### Параметры (0-100)
hunger, happiness, hygiene, energy, discipline, strength

### Деградация
Раз в час: голод, счастье, гигиена и дисциплина убывают на 5, энергия — на 3. Расчёт ленивый: выполняется при обращении к питомцу, от отметки `last_updated`. Фоновой задачи нет, поэтому простой бота не останавливает время.

### Действия и эффекты
- feed → +hunger, +xp
- play → +happiness, +xp
- wash → +hygiene, +xp
- sleep → +energy, +xp (требует energy < 100)
- train → -energy, +discipline, +strength, +xp (требует energy >= 20)

У каждого действия свой кулдаун.

### Рост питомца
```
Зарождение (10 XP) → Яйцо (50 XP) → Малыш (150 XP) → Подросток (300 XP) → Взрослый
                            ↑
                     Выбор вида (случайно)
```

Условие роста: XP >= порога И все параметры >= 60.

## Безопасность

- Проверка уровня доступа на каждой административной команде
- Проверка подписи Telegram initData на всех запросах к API
- Реальные ID пользователей не покидают базу данных
- Параметры запросов к API валидируются, тело разбирается безопасно
- Токен бота и настройки хранятся в `.env` и не попадают в репозиторий

## Известные ограничения

- Черновики рассылок хранятся в памяти процесса (`StateMemoryStorage`) и теряются при перезапуске
- SQLite плохо переносит параллельную запись: при больших рассылках стоит перейти на PostgreSQL
- Автоматических тестов нет
- Рассылка, прерванная падением процесса, остаётся в статусе SENDING и требует ручного вмешательства
